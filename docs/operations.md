# Операции: обновление, бэкапы, ключи

Документ для сопровождения установки. Команды выполняются от root на сервере панели в каталоге `/opt/vps-panel`, если не указано другое.

## 1. Обновление панели

### Подготовка

```bash
vps-panel status
df -h /var/lib/docker
```

Перед обновлением желательно иметь свежую резервную копию панели. Обновление образов и панели выполняет host-служба; контейнер панели не имеет доступа к Docker.

### Обновление

В `tmux`/`screen`, чтобы обрыв SSH не прервал процесс:

```bash
tmux new -s panel-update
vps-panel update 1.21.2 --force
```

Без `--force` версия берётся из аргумента или последнего стабильного релиза; `--force` нужен, если в `.env` уже записана целевая версия, а контейнер ещё старый.

Из интерфейса: "Настройки" - "Версия панели" - "Обновить". Служба пишет ход в `/opt/vps-panel/data/deploy.json`.

### Проверка

```bash
vps-panel status
curl -fsS https://<домен>/api/health
docker logs --tail 50 vps-panel-panel-1
```

Ожидается версия из `.env`, healthy-контейнеры и `{"ok":true,"version":"..."}`. Проверьте, что агенты снова online.

### Если обновление застряло

Симптомы: полоса прогресса исчезла, кнопка проверки неактивна, версия не изменилась.

```bash
cat /opt/vps-panel/data/deploy.json
cat /opt/vps-panel/data/update/request.json
systemctl status vps-panel-update.path vps-panel-update.service --no-pager -l
journalctl -u vps-panel-update.service -n 150 --no-pager
ps -ef | grep -E '[v]ps-panel|[d]ocker compose'
```

Если заявка `request.json` есть, но служба не запущена:

```bash
systemctl reset-failed vps-panel-update.path vps-panel-update.service
systemctl start vps-panel-update.service
journalctl -u vps-panel-update.service -f
```

Не удаляйте `request.json`, пока не убедились, что процесс обновления не работает. Если он завис:

```bash
systemctl stop vps-panel-update.service
fuser -v /run/vps-panel-update.lock
```

Lock-файл не удалять: после остановки процесса блокировка снимется сама.

Если обновление не запускается из интерфейса, выполните его вручную в `tmux`/`screen`:

```bash
vps-panel update 1.21.2 --force
```

### Известная проблема 1.20.2/1.21.0

В этих релизах в `/usr/local/bin/vps-panel` попал JSDoc-комментарий, и команды `vps-panel` падали с:

```text
/usr/local/bin/vps-panel: line 926: ..: command not found
```

Исправление - в 1.21.1+. Если CLI на хосте сломан, поставьте исправленный файл вручную и затем обновитесь:

```bash
cd /tmp
curl -fsSLO https://github.com/iKonan-ru/vps-panel/releases/download/v1.21.2/vps-panel
curl -fsSLO https://github.com/iKonan-ru/vps-panel/releases/download/v1.21.2/release.sha256
sha256sum -c release.sha256 --ignore-missing
install -m 755 vps-panel /usr/local/bin/vps-panel
vps-panel update 1.21.2 --force
```

Не откатывайтесь на 1.20.2/1.21.0 без такой замены CLI.

### Откат

```bash
vps-panel rollback
```

Откат использует `PANEL_PREV_VERSION` и тот же механизм обновления. Перед откатом проверьте, что в предыдущем релизе исправлен host-скрипт.

## 2. Обновление агентов

Агенты обновляются из образа панели: автоматически (если включено) или вручную в карточке сервера / на странице серверов.

После обновления проверьте:

- версия агента `0.4.0+`;
- в карточке сервера агент online;
- в логах панели нет `агент использует канал v2`.

Когда все агенты перешли на v3:

```bash
grep '^AGENT_V2_COMPAT=' /opt/vps-panel/.env
```

Если там `1` или строки нет, поставьте `AGENT_V2_COMPAT=0` и перезапустите панель:

```bash
vps-panel restart
```

После этого v2 отклоняется. Убедитесь, что все агенты снова online; старый агент останется offline до обновления.

## 3. Резервные копии и восстановление

- Панель пишет копии в формате v2 (AES-256-GCM).
- Копии серверов при скачивании - v3 (потоковый AES-256-GCM).
- Старые копии v1 (openssl) читаются при восстановлении/загрузке, но новые копии в v1 не создаются.

Восстановление панели:

```bash
vps-panel restore /root/vps-panel-backup-<дата>.tar.gz.enc
```

Пароль можно передать в `BACKUP_PASSWORD`; `-y` отключает подтверждение. Команда расшифрует архив, остановит панель, заменит данные и проверит ответ. Прежние данные остаются в `/opt/vps-panel/data/before-restore-<время>`.

Проверяйте восстановление на тестовом сервере, а не только наличие скачанного файла. Для v1 используйте старую команду `openssl enc` из docs/install.md; для v2/v3 - только `vps-panel restore`.

## 4. Ротация ключей

### Ключ SSH панели (`data/panel_ssh_ed25519`)

Нужен для установки и очистки агентов по ключу. Автоматической ротации нет.

1. Сгенерируйте новую пару вне каталога данных:
   ```bash
   ssh-keygen -t ed25519 -N '' -C 'vps-panel-rotation' -f /root/panel_ssh_new
   ```
2. Добавьте `/root/panel_ssh_new.pub` в `/root/.ssh/authorized_keys` на всех управляемых серверах.
3. Проверьте вход новым ключом на одном сервере.
4. Замените файлы панели:
   ```bash
   install -m 600 /root/panel_ssh_new /opt/vps-panel/data/panel_ssh_ed25519
   install -m 644 /root/panel_ssh_new.pub /opt/vps-panel/data/panel_ssh_ed25519.pub
   vps-panel restart
   ```
5. Проверьте установку/очистку на тестовом сервере и удалите старый публичный ключ из `authorized_keys`.

### Ключ панели для агентов (`data/panel_agent_ed25519.pem`)

Агенты доверяют этому ключу и не подключаются к панели с другим. Ротация требует обновить ключ в конфиге каждого агента; автоматической процедуры нет.

Порядок: запланировать обслуживание, заменить ключ, переустановить/перенастроить агентов с новым публичным ключом, проверить v3-подключение. Старые агенты останутся offline. При компрометации ключа это единственный безопасный путь.

### Токены агентов

Постоянный токен создаёт агент при регистрации; панель хранит только хеш. Для перевыпуска используйте "Переустановить агент" в карточке сервера: создаётся новый одноразовый токен, старый перестаёт действовать.

### `SESSION_SECRET`

Ключ шифрует доступы, ключи AWG, токены 3X-UI и TOTP-секреты в базе. В 1.21.x **нет автоматической перешифровки** при смене `SESSION_SECRET`. Не меняйте его на работающей панели без отдельного плана миграции: старые значения станут нечитаемыми. При компрометации - восстановление из доверенной копии, смена всех секретов и перевыпуск доступов.

### Telegram-токен

Перевыпустите токен в BotFather, сохраните новый в настройках панели и проверьте уведомления. Агентам токен не передаётся с версии 1.20.0.

### Пароль резервных копий

Смена пароля действует на новые копии. Старые копии требуют старый пароль; перешифровки нет. Проверьте восстановление после смены.

## 5. Инцидент

1. Ограничьте доступ к панели и серверам, сохраните логи.
2. При подозрении на утечку `SESSION_SECRET`/базы - не меняйте секрет вслепую, сначала оцените зашифрованные данные.
3. Отзовите SSH-ключи и токены агентов, переустановите агентов на затронутых серверах.
4. Перевыпустите Telegram-токен и пароль резервных копий.
5. Восстановите панель из доверенной копии и проверьте целостность.
6. Зафиксируйте хронологию и решение по L-05/рискам в risk register (вне репозитория).

```bash
vps-panel status
vps-panel logs panel
vps-panel logs caddy
cat /opt/vps-panel/data/deploy.json
cat /opt/vps-panel/data/update/request.json
systemctl status vps-panel-update.path vps-panel-update.service --no-pager
journalctl -u vps-panel-update.service -n 200 --no-pager
docker logs --tail 100 vps-panel-panel-1
```
