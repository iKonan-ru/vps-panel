# Транзакция смены SSH-порта

До `commit` независимый recovery возвращает исходные настройки. После проверки
нового входа (`verified`) recovery сохраняет оба проверенных порта, чтобы потеря
ответа панели или отказ `finish` не закрыли рабочий путь.

`prepare`, `finish` и recovery берут `/run/vps-portsync.lock`. Вызов port-sync из
транзакции наследует тот же дескриптор через `--lock-fd`. Обычный port-sync берёт
замок до чтения желаемого состояния, поэтому ожидающий таймер не применяет старый
снимок после завершения перехода.

Журнал перехода содержит исходные SSH-правила UFW и правила для нового порта.
Port-sync сохраняет их, включая ограничения источников, пока журнал существует.
Ручные правила при этом не становятся управляемыми правилами port-sync.

Перед изменением `ssh_port` сохраняются текст и права конфигурации port-sync.
Сначала применяется firewall с защитой обоих путей, затем SSH переключается на
новый порт. Удаление журнала означает завершение операции. Старые управляемые
правила удалит следующий port-sync; ручные правила остаются ручными.

При отказе восстанавливаются конфиг port-sync, оба SSH-слушателя и их правила UFW,
после чего повторно применяется port-sync для согласования его журнала с firewall.
Отказ одного шага восстановления не отменяет остальные. Ошибки возвращаются
вызывающему коду, журнал остаётся для повторной попытки и независимого recovery.
UFW сначала добавляет необходимые правила, затем удаляет устаревшие; ошибка команды
не считается успехом, а журнал намерения позволяет повторить частичное применение.

## Автоматические проверки

Из корня репозитория:

```sh
python3 -m unittest discover -s apps/agent/internal/sshport -p '*_test.py' -v
```

Тот же набор запускается через `go test ./internal/sshport` и общий CI агента.
Тесты выполняют настоящий Python-код port-sync и запись временных файлов.
Команды SSH, UFW, iptables и systemd заменены заглушками; отдельные процессы
проверяют настоящий flock, наследование дескриптора и чтение конфига после ожидания.

## Испытание на отдельной Linux VM

Использовать одноразовую VM с консольным доступом, systemd, OpenSSH, UFW и fail2ban.
Проверить обычный ssh.service и socket activation с KillMode=process, IPv4 и IPv6.
Новое подключение проверять с другой машины, а не через уже открытую SSH-сессию.

1. Подготовить и подтвердить переход. Проверить свежий вход через оба порта.
2. Временно обернуть vps-portsync: передать аргументы и унаследованные дескрипторы
   настоящему скрипту, после его успешного применения вернуть код 1 один раз.
3. Вызвать finish. Проверить ошибку, точное восстановление конфига и прав файла,
   наличие журнала verified, доступность обоих портов и сохранность текущих сессий.
4. Запустить vps-portsync.service и дождаться периодического запуска. Повторить
   свежие подключения через оба порта и сверить UFW с state.json port-sync.
5. Повторить с постоянным отказом port-sync, затем убрать отказ и дать независимому
   пятиминутному recovery восстановить состояние без работающей панели.
6. Повторить с отказом reload SSH после успешного port-sync и с остановкой процесса
   finish между записью конфига и удалением журнала.
7. Повторить finish с тем же token. Проверить новый порт, удаление журнала и то,
   что следующий port-sync убрал старые управляемые правила без потери новых.

Локальные заглушки не подтверждают реальное поведение sshd, socket activation,
systemd-таймеров, fail2ban и сетевого стека UFW. Это отдельный интеграционный этап.
